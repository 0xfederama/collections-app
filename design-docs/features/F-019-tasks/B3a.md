## Design of the migration (applies to B3a..B3f)
Operations move from the old generated strict server to Huma one feature at a time; the old hand-written `api/openapi.yaml` and `oapi.gen.go` stay untouched until B5 (they remain the reference contract for the web until the generated one is final).
- Old routes are mounted first, then the Huma routes of the migrated features on the SAME chi router: chi replaces a handler registered twice for the same method+path, so Huma wins. The old guard middleware only wraps old routes.
- A migrated operation's old handler method is DELETED from `internal/httpapi`. `httpapi.Server` embeds `oapi.StrictServerInterface` (nil, with a `// TEMPORARY until B5: operations already served by Huma` comment) so it keeps satisfying the interface; the nil methods are unreachable because Huma overrides the route (a test proves each migrated route is served by Huma, see T4).
- `httpapi.Deps` keeps its shape in B3a (tests build it); `NewRouter` is the temporary composition point; `cmd/api` keeps calling it.
- Feature layout: `handler.go` (HTTP only) → `service.go` (rules; declares `Store`/`Repo` interfaces) → `repository.go` (the only file with sqlc) + `model.go`. Plain reads go from the handler through a small consumer-declared interface to the repository (no pass-through service).
