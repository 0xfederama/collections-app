## Goal
Migration `000001_init` creates the full DATA_MODEL §2 schema plus the `pg_trgm` extension. sqlc is wired through the `go.mod`
`tool` directive and `make generate`, and its generated code is committed under `internal/database/sqlc`. `make check` gains a
sqlc drift check and a migrations up → down → up test on testcontainers Postgres. This PR is the schema half of the **C1
user review gate**: the user reviews the migration before B-03 starts (D-045).

## Scope
**Migration** (create the pair with `make migration name=init`, giving `db/migrations/000001_init.{up,down}.sql`):
- `CREATE EXTENSION IF NOT EXISTS pg_trgm;` first, then the tables in FK order: `workspaces`, `workspace_settings`,
  `trash_batches`, `folders`, `lists`, `attachments`, `items`, `item_content_versions`.
- Semantics exactly as DATA_MODEL §2: every column, type, default, CHECK, UNIQUE, composite FK with its ON DELETE action, and
  index (including the partial `WHERE deleted_at IS NULL` predicates and the `gin (lower(title) gin_trgm_ops)` index).
  Spell out the columns the doc elides (`created_at, updated_at` → `TIMESTAMPTZ NOT NULL DEFAULT now()`; lists/items
  `deleted_at`/`trash_batch_id` "as folders").
- **D-051:** `trash_batch_id UUID NULL REFERENCES trash_batches(id)` with **no** `ON DELETE` clause on folders, lists, items.
- Name every constraint and index explicitly, using `<table>_<column(s)>_{pkey,key,fkey,check,idx}` (e.g. `items_image_source_check`,
  `items_price_range_check`, `folders_active_parent_idx`, `items_title_trgm_idx`), so later tasks can map constraint names to
  domain errors. Short, readable names beat mechanical ones. Keep them under the 63-byte limit.
- Up header comment: "Initial schema (DATA_MODEL §2)". Down header comment: destructive, drops all data (DATA_MODEL §8). Down
  drops the tables in reverse order, then `DROP EXTENSION IF EXISTS pg_trgm;`.
- Any semantic deviation from DATA_MODEL beyond D-051: **stop and ask** (AGENT_WORKFLOW §7). Syntax-only adjustments are fine; list them in the PR.
- Keep the compose `migrate` guard (D-037). With a migration present it now just runs `migrate up`.

**sqlc**
- `go get -tool github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1`, run as `go tool sqlc` (D-035). Report in the PR any direct-dependency
  version that moved as a side effect (e.g. pgx, testcontainers), and note it if the Docker build got noticeably slower
  (`go mod download` now fetches tool deps too).
- `sqlc.yaml` (version 2): engine `postgresql`, schema `db/migrations` (confirm sqlc ignores `*.down.sql`; if it doesn't, list the
  up files explicitly), queries `db/queries`, Go output `internal/database/sqlc`, package `sqlc`, `sql_package: pgx/v5`,
  `emit_empty_slices: true`, `emit_pointers_for_null_types: true`, and the D-049 overrides (`uuid` → `github.com/google/uuid.UUID`,
  nullable `uuid` → `uuid.NullUUID`, `timestamptz` → `time.Time`). Verify the exact override keys against the v1.31.1 docs.
- Queries: the IMPLEMENTATION_PLAN row says "empty query files compiling". Find out whether sqlc v1.31.1 fails or generates nothing
  with zero queries. If it needs at least one, add **one** file `db/queries/schema.sql` with a single query that the migration test
  uses (e.g. `-- name: CountWorkspaces :one`). No domain queries: those belong to B-05+.
- Commit the generated code (D-019). Never hand-edit it. Confirm golangci-lint v2 skips it (default `generated: lax`) and that
  goimports and gofmt are happy.

**Makefile**
- `generate` = `go tool sqlc generate` (update the help comment; B-03 appends oapi-codegen to it).
- New `check-generate`: run `$(MAKE) generate`, then fail with a clear message if
  `git status --porcelain -- internal/database/sqlc db/queries sqlc.yaml` is non-empty. This also catches new untracked files, which
  `git diff --exit-code` alone misses.
- `check: fmt-check lint check-generate test check-compose check-docker`. Add `check-generate` to `.PHONY`.
- The migrations test runs inside `test` (it's a normal `go test`), so `check` needs no separate migration target.

**Tests** in `internal/database/migrations_test.go` (package `database_test`). They use their own testcontainers Postgres
(same image tag and wait strategy as `router_test.go`; one shared container per test binary is fine) and the
`github.com/golang-migrate/migrate/v4` library v4.20.1 (D-050) with its pgx/v5 database driver and the file source on
`../../db/migrations`. Verify the driver import path and URL scheme for v4.20.1. Test names below:
- `TestMigrations_UpDownUp`: up → all 8 tables and the `pg_trgm` extension exist → down → only `schema_migrations` is left and the
  extension is gone → up again with no error. Use a fresh database (or container) so it doesn't fight the other tests.
- `TestMigrations_DownWithData`: up, insert one valid row into every table (workspace → settings → folder → list → attachment → item
  with that attachment → content version, plus one trash batch with a trashed list), down, up.
- `TestSchema_Constraints` (table-driven, direct SQL against a migrated DB; each case runs in its own tx that is rolled back), asserting
  the SQLSTATE and constraint name:
  - list referencing a folder of **another** workspace → FK violation (composite FK)
  - item with both `image_url` and `image_attachment_id` → CHECK (AT-07 DB part; name it `TestAT07_…` or tag the case)
  - `deleted_at` set without `trash_batch_id` (and the reverse) → CHECK
  - `price_min > price_max` → CHECK; a price without `currency` → CHECK
  - folder whose `parent_folder_id` = its own id → CHECK
  - `metadata = '[]'` → CHECK; `kind = 'Movie'` → CHECK
  - name of 0 and 201 chars → CHECK; `streaming_country_code = 'it'` → CHECK
  - `workspace_settings` defaults are `IT` / `EUR` / `20` when inserted with only `workspace_id`
  - **D-051:** deleting a `trash_batches` row still referenced by a trashed folder → FK violation (23503), and the row is unchanged
  - **D-051:** `DELETE FROM workspaces` with trashed folders/lists/items and their batches present → succeeds and leaves every table
    empty. **If this fails, stop and report it in the brief's Questions section** (D-051 assumes it works).
- A `test-writer` subagent may draft the constraint cases. You review them and run them yourself.
