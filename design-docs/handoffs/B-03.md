## Scope
**Prototype first (D-041), before writing the whole spec.** Write the spec for `GET`/`PATCH /api/v1/items/{id}` and `POST /api/v1/folders`
only, generate, and check in the generated Go that:
1. `If-Match` arrives in the request object and `ETag` / `Location` are typed response headers the handler must set.
2. Problem responses with `application/problem+json` produce usable typed responses (e.g. a 412 carrying `current_version`).
3. The Item response with metadata as a discriminated `oneOf` (DATA_MODEL §2.1 end) generates code that compiles and that a handler can build.
4. What the strict handler does with unknown JSON fields, and with a missing **required** header.
Record the findings in this brief's Progress section. If any of 1–3 can't be expressed cleanly, **stop and ask** in Questions before going on.

**Spec (`api/openapi.yaml`, one file)**
- `openapi: 3.0.3`, `info.version: 0.1.0`, `info.description` with the conventions of API.md §1/§3/§6 (incl. "every response carries
  `X-Request-Id`" and the body limits). One `servers` entry `/`, and **full paths** (`/api/v1/...`, plus `/healthz` and `/readyz` under a
  `health` tag) so the health probes are documented too.
- Every API.md §5 endpoint, with `operationId` camelCase verbNoun (`updateItem`, `listItems`, `moveFolder`, `reorderListItems`,
  `restoreTrashBatch`, ...), one tag per resource group, request bodies, query and path params with their limits (`limit` 1–200 default
  50, `offset` ≥ 0, `q` 1–200 for search, `sort` enum), and **every response code from API.md §4 that the endpoint can return**.
- Components, at least: `Problem`, `ValidationProblem` (with `errors[{field,message}]`), `Page`, `Price`, `Image` (url | upload,
  `oneOf` + discriminator on `source`), `PathSegment`, `Folder`, `List`, `Item`, `ItemSummary`, `Content`, `ContentVersionInfo`, `Settings`,
  `TrashEntry`, `Tree`, the per-kind metadata schemas, and reusable `responses` for each problem (`NotFound`, `VersionConflict`,
  `PreconditionRequired`, `ValidationFailed`, ...) and `parameters`/`headers` (`IfMatch`, `ETag`, `Location`).
- Field rules from DATA_MODEL §2/§2.1 (lengths, enums, patterns, money pattern `^\d{1,10}\.\d{2}$`, UUID/date-time formats, nullable).
  The server still validates in Go; the spec documents the rules and types the clients.
- **ETag:** declared as a response header on every `GET` of a single resource and every mutation that returns one (API.md §1/§3).
  **`If-Match`:** declare it `required: false` with a description saying it is required and a missing one returns 428. A `required: true`
  header makes the generated wrapper answer 400, which would break API.md's 428 (confirm this in the prototype, point 4).
- **Do not** put `X-Request-Id` in per-operation response headers: it would make every generated response type carry it, and B-04 sets it
  in middleware. Document it in `info.description` only.
- **Metadata:** in `Item` responses, metadata is a `oneOf` per kind with `kind` as the discriminator, as DATA_MODEL §2.1 says. In
  **requests** (create and PATCH), `kind` can be absent, so `metadata` is a free-form object (`type: object`) whose description points at
  the per-kind schemas. Go validates it either way (B-07). If the prototype shows the response union is unworkable, ask (see above).
- Image `PUT` accepts `multipart/form-data` (`file`, binary) **or** `application/json` (`{ url }`). Attachment `GET`s return
  `image/jpeg|png|webp` binary with the `Cache-Control` header described.
- `additionalProperties: false` on request body schemas (documents the `400 unknown_field` rule; B-04 enforces it).
- **Examples**: at least one realistic named example for every 2xx JSON response and request body, plus one example per problem `code`.
  They must validate against their schemas. W-02 builds MSW mocks from them, so use stable fake UUIDs and plausible data (a movie with
  streaming, a motorcycle, a list with `path`, a trash entry, a content version list).
- Keep the spec readable for the user's review: logical order (health, settings, tree, folders, lists, items, image, content, search,
  trash), short descriptions, no duplicated schemas.
- If writing the spec shows a gap or contradiction in API.md, fix API.md in the parent **in the same PR window** and add a DECISIONS entry
  (AGENT_WORKFLOW §7). Any **semantic** change to the API (an endpoint, field, status code or header not in API.md): stop and ask.
