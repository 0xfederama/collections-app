## Rules of the exercise
- Work in a **fresh clone** in a new temp dir: `git clone --recurse-submodules https://github.com/0xfederama/collections-app.git`.
  Don't reuse anything from `/Users/federico/Developer/collections-app` (no copied `.env`, `node_modules`, data, images).
- Read **only** the READMEs (and files they tell you to open). Don't read design-docs, CLAUDE.md files or code to "figure things out":
  if the docs don't say it, that is a finding. Exception: this brief and STATUS.md for bookkeeping.
- **Never touch the user's data.** Before running any command, check which compose project and ports it uses
  (`./deploy/dev` = the user's data: **never run it**, not even from the clone, it shares the project name). For local checks use the clone's
  `./deploy/test` only if `docker ps` shows no `collections-app-test` stack in use by another session; otherwise ask. For prod use
  `PROD_PROJECT=collections-app-q04 ./deploy/prod …` with a throwaway data location, and tear everything down at the end
  (`down --volumes` on your own projects only). If a README step would make you run dev, record that as a finding and use test instead.
- Keep a log: every command, every place you had to guess, every error.

## Steps
1. Prerequisites as the README lists them (versions of Docker, git, Node, Go where needed); note anything missing or unclear.
2. Local run as a new user would do it (test env per the rules above): app reachable, create a folder/list/item, upload an image.
3. Quality gates as documented (`make check` in backend, `npm run check` in web) from the clone: they must pass on a fresh checkout
   (needs Docker). Note anything the docs forgot (e.g. Node needed for the backend spec lint, first-run golangci-lint compile time).
4. Prod path from `deploy/README.md`: first start, `/readyz`, a backup, an upgrade dry run (`git pull --recurse-submodules` + rebuild),
   restore drill on your own project. Note unclear steps (host paths, UIDs, `.env` values, Tailscale opt-in).
5. Fix the docs: parent `README.md` / `deploy/README.md` directly (pathspec commits); backend README via a small backend PR
   (`docs/Q-04-readme-fixes`, own worktree); **web README fixes**: list them in Questions for the web orchestrator (don't edit the web repo).
